# insane-node-rest-api

A compact, fully-typed REST API starter using Node.js, TypeScript, Express, Prisma (MySQL/MariaDB), and tsoa for OpenAPI generation.

## Features

- TypeScript + Express server
- Prisma ORM with generated client and committed migrations
- OpenAPI (Swagger) spec and routes generated by `tsoa`
- JWT authentication: short-lived access tokens, and refresh tokens rotated on every use, with reuse detection that ends the affected device's session
- Memos with tags, shared between users with a role per memo: create, read, edit, delete, assign
- Per-IP rate limiting on login, register and refresh
- Liveness and readiness health checks, and graceful shutdown
- Access log file, rotated daily
- ESLint, Prettier and Vitest for linting, formatting and tests, run in CI on GitHub Actions

## Prerequisites

- Node.js >= 26
- A MySQL or MariaDB instance with two databases (main & shadow) accessible from your environment
- npm (or a compatible package manager)

## Environment

Copy the example file, then fill in your values:

```bash
cp .env.example .env
```

Every setting is checked at startup. A missing or malformed value stops the app with a message naming the variable. An empty value counts as unset.

**Required**

| Variable                              | Example                 | Description                                                                                                      |
| ------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `PORT`                                | `3000`                  | Port the API listens on (1–65535).                                                                               |
| `CORS_ORIGIN`                         | `http://localhost:5173` | Origin of the frontend that calls the API, here a Vite dev server. Only one origin is allowed.                   |
| `JWT_SECRET`                          |                         | Signs access tokens.                                                                                             |
| `JWT_REFRESH_SECRET`                  |                         | Signs refresh tokens.                                                                                            |
| `JWT_REFRESH_HASH_SECRET`             |                         | Key for the HMAC of refresh tokens, which is what the database stores.                                           |
| `JWT_ACCESS_TOKEN_EXPIRES_IN_MINUTES` | `5`                     | Access token lifetime, a positive integer.                                                                       |
| `JWT_REFRESH_TOKEN_EXPIRES_IN_DAYS`   | `7`                     | Refresh token lifetime, a positive integer.                                                                      |
| `DATABASE_USER`                       | `db_user`               | Database user.                                                                                                   |
| `DATABASE_PASSWORD`                   | `db_password`           | Database password.                                                                                               |
| `DATABASE_HOST`                       | `localhost`             | Database host.                                                                                                   |
| `DATABASE_PORT`                       | `3306`                  | Database port (1–65535).                                                                                         |
| `DATABASE_NAME`                       | `db_name`               | Main database.                                                                                                   |
| `SHADOW_DATABASE_NAME`                | `shadow_db_name`        | Shadow database, used by `prisma migrate dev` to detect schema drift. Required, although the app doesn't use it. |

Use three different long random values for the JWT secrets, for example from `openssl rand -hex 32`. `JWT_SECRET` and `JWT_REFRESH_SECRET` in particular must differ: with the same secret, a refresh token would also pass as an access token.

**Optional**

| Variable                  | Default                    | Description                                                                                                    |
| ------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `NODE_ENV`                | `development`              | `development`, `production` or `test` (see below).                                                             |
| `DOCS_ENABLED`            | `true`, except production  | Serve Swagger UI at `/docs`.                                                                                   |
| `ACCESS_LOG_ENABLED`      | `true`, except tests       | Write the access log file (see [Logging](#logging)).                                                           |
| `ACCESS_LOG_DIR`          | `logs`                     | Folder for `access.log`. A relative path is resolved against the working directory.                            |
| `TRUST_PROXY`             | unset: no proxy is trusted | Behind a reverse proxy: the number of proxy hops (e.g. `1`), or trusted addresses or subnets, comma-separated. |
| `RATE_LIMIT_ENABLED`      | `true`                     | Turn the rate limits on or off.                                                                                |
| `RATE_LIMIT_LOGIN_MAX`    | `10`                       | Login requests per client IP per 15 minutes.                                                                   |
| `RATE_LIMIT_REGISTER_MAX` | `5`                        | Register requests per client IP per hour.                                                                      |
| `RATE_LIMIT_REFRESH_MAX`  | `60`                       | Refresh requests per client IP per 15 minutes.                                                                 |

The `*_ENABLED` settings accept exactly `true` or `false`.

`NODE_ENV` changes the following:

- `production`: the refresh cookie gets `Secure`, so browsers only send it over HTTPS. `/docs` is off and there is no console request log.
- `test`: no access log file and no console request log.
- `development`, or anything else: Swagger UI at `/docs`, the access log file and a colored console request log.

## Install

1. Install dependencies:

   ```bash
   npm install
   ```

2. Create `.env` (see [Environment](#environment)):

   ```bash
   cp .env.example .env
   ```

3. Generate the Prisma client, which isn't committed:

   ```bash
   npm run prisma:generate
   ```

4. Apply the database migrations:

   ```bash
   npx prisma migrate deploy
   ```

5. Run the development server with hot reload:

   ```bash
   npm run dev
   ```

The OpenAPI spec, routes and API types are committed, so there's nothing to generate for them (see [OpenAPI / Swagger](#openapi--swagger)).

## Database Migrations

Migrations live in `prisma/migrations` and are committed. Apply them to a new or existing database with:

```bash
npx prisma migrate deploy
```

After changing `prisma/schema.prisma`, create and apply a new migration during development (this uses the shadow database), then commit it:

```bash
npx prisma migrate dev --name <describe-the-change>
```

Never edit a migration that has already been applied somewhere: Prisma stores a checksum of each one and reports a mismatch.

## Production

Build the project (generates the Prisma client, routes/spec via `tsoa` and API types, then compiles TypeScript):

```bash
npm run build
```

Start the compiled app:

```bash
npm run start
```

## Authentication & Rate Limiting

- `POST /auth/register` creates a user and returns 201.
- `POST /auth/login` returns an access token in the body. It sets the refresh token as a cookie: `HttpOnly`, `SameSite=Strict`, limited to the `/auth` path, and `Secure` in production.
- Protected endpoints take the access token as `Authorization: Bearer <token>`.
- `POST /auth/refresh` exchanges the cookie for a new access token and a new refresh token. Each refresh token works once:
  - If one that has already been used turns up again, it's treated as stolen. Every token from that login is revoked, so that device, and whoever copied the token, must log in again. The user's other devices stay logged in.
  - Two refreshes with the same token at the same moment don't count as reuse: one succeeds and the other gets 401.
- `POST /auth/logout` needs only the cookie, so it also works once the access token has expired. It ends that login's session and always clears the cookie.

Since the cookie is `SameSite=Strict`, the frontend must be on the same site as the API: the ports may differ, as with `localhost:5173` and `localhost:3000`. It must also send its requests with credentials, e.g. `credentials: 'include'` in `fetch`.

Login, register and refresh are rate-limited per client IP. The limits are set by the `RATE_LIMIT_*` settings in [Environment](#environment).

- **Over the limit:** the client gets `429 {"message": "Too many requests, please try again later"}` with `RateLimit-Policy`, `RateLimit` and `Retry-After` headers.
- **One instance only:** counts are kept in memory. Several instances would each count separately, and would need a shared store such as Redis.
- **Behind a reverse proxy:** set `TRUST_PROXY`, or all clients share the proxy's IP and therefore one limit. Avoid `TRUST_PROXY=true`, which lets clients spoof their IP through `X-Forwarded-For`.

## Memos, Tags & Users

All of these endpoints need the access token. Users and memos are identified by their uuid; numeric database ids are never returned.

A memo is shared by assigning users to it, each with a role on that memo: `USER`, `MOD` or `ADMIN`. The role is separate from the user's global role. Whoever creates a memo is its author and is assigned as its `ADMIN`. What a user may do with a memo:

| Action                       | Author        | ADMIN    | MOD            | USER |
| ---------------------------- | ------------- | -------- | -------------- | ---- |
| Read                         | yes           | yes      | yes            | yes  |
| See who it's shared with     | yes           | yes      | yes            | yes  |
| Edit title, content and tags | yes           | yes      | yes            | no   |
| Delete                       | yes           | yes      | no             | no   |
| Assign other users           | by their role | any role | only as `USER` | no   |
| Remove others' assignments   | by their role | any      | `USER` ones    | no   |

The author's right to edit and delete doesn't depend on their role, so they keep it even if that role is lowered. Assigning and removing assignments depend on the role alone, with these exceptions: anyone can remove their own assignment (leave the memo), and the assignments they made as long as their role is at least as high as the assignee's. The author's assignment can't be removed, not even by the author, so the memo always stays in their list.

**Memos**

- `GET /memos` lists the memos assigned to you, including your own, with your role on each. Filter by tags with `?tags=a&tags=b` (up to 10 tags). `match=all`, the default, returns memos carrying every given tag; `match=any` returns memos carrying at least one.
- `POST /memos/create` creates a memo from `title`, `content` and optional `tags`, and returns it with 201.
- `GET /memos/{memoUuid}` returns your assignment to one memo, with the memo.
- `PATCH /memos/{memoUuid}` changes a memo's `title`, `content` and `tags`, and returns the memo. Fields left out stay as they are. Tags you send replace all current ones, and `tags: []` removes them all.
- `DELETE /memos/{memoUuid}` deletes a memo for everyone it is assigned to and returns 204. Its assignments and tag links are deleted with it; the tags themselves stay, as other memos may use them.
- `GET /memos/{memoUuid}/assignments` lists everyone a memo is assigned to, oldest assignment first (so the author usually comes first). Each entry has the assignee's `userUuid`, `username`, `displayName` and `role` on the memo, `assignedAt`, and the same three fields for whoever assigned them (`assignedByUuid`, `assignedByUsername`, `assignedByDisplayName`). Email addresses and global roles are never included.
- `DELETE /memos/{memoUuid}/assignments/{userUuid}` removes a user's assignment to a memo and returns 204. The memo then no longer shows up in their list, and they lose access to it. Removing the author returns 403. It returns 404 if the user isn't assigned to the memo.
- `POST /memos/assign` assigns a memo to another user, given `memoUuid`, `userUuid` and an optional `role` (`USER` by default), and returns 201. It returns 404 if the user doesn't exist, and 409 if they are already assigned.

A memo in a response has `uuid`, `title`, `content`, `authorUuid`, `authorUsername`, `authorDisplayName` (null if the author has none), `createdAt` and `tags`. Tags are stored lowercased and returned sorted.

A memo you have no access to gets the same 403 as one that doesn't exist, `{"message": "Memo not found or you do not have access to it"}`, so the API doesn't reveal which memos exist. An action your role doesn't allow also gets 403, with a message saying who may do it. Invalid bodies and query parameters, including unknown fields, get `422 {"message": "Validation failed", "details": {...}}`.

**Tags**

- `GET /tags` lists the tags on the memos assigned to you, sorted by name, each with how many of those memos carry it.

**Users**

- `GET /users/me` returns your profile.
- `GET /users` lists other users, sorted by username, for example to pick whom to assign a memo to. It returns only their uuid, username and display name, and never lists you. `search` matches the username or display name, ignoring case. `limit` (1–50, 20 by default) and `offset` page through the results.

## Logging

Requests are logged in Apache `combined` format to `access.log`, rotated daily, in the `logs` folder of the working directory. Set `ACCESS_LOG_DIR` to use another folder (a relative path is resolved against the working directory). File logging is off when `NODE_ENV=test`, unless `ACCESS_LOG_ENABLED=true` is set; `ACCESS_LOG_ENABLED=false` turns it off in any environment.

Outside production and tests, requests are also logged to the console in a short, colored format.

## Health Checks & Shutdown

For load balancers and orchestrators, without auth and not in the access log:

- `GET /health` (liveness): `200 {"status":"ok"}` while the process is running. It doesn't touch the database.
- `GET /health/ready` (readiness): `200 {"status":"ok"}` when the database answers, `503 {"status":"unavailable"}` when it doesn't.

On `SIGTERM` or `SIGINT` the server stops accepting connections, lets requests in progress finish, closes the database pool and exits. If that takes longer than 10 seconds, or a second signal arrives, it exits right away with code 1.

## OpenAPI / Swagger

After changing a controller or DTO, regenerate the OpenAPI spec and routes (this is also part of `build`), then commit both files. CI fails if they are out of date.

```bash
npm run tsoa:spec
npm run tsoa:routes
```

The generated spec is available at `src/docs/swagger.json`, and the running app serves Swagger UI at `/docs`. It is off when `NODE_ENV=production`, unless `DOCS_ENABLED=true` is set; `DOCS_ENABLED=false` turns it off in any environment.

## API Types

`generated/api.ts` holds TypeScript types (and a fetch client) for the API, generated from `src/docs/swagger.json`. It is committed because [insane-react-pwa](https://github.com/lucasdee/insane-react-pwa) takes its API types from it. After regenerating the spec, regenerate this file too (this is also part of `build`) and commit it. CI fails if it is out of date.

```bash
npm run types:generate
```

## Testing

The tests need no database and no `.env`: they run against an in-memory fake of Prisma, with settings from `vitest.config.mts`.

Run tests in watch mode with:

```bash
npm run test
```

Run tests once, with coverage:

```bash
npm run test:coverage
```
